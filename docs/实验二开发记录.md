## 二、逐次提交说明

### 第 1 次：Entity 层

**提交**：`58ce7e9`　**文件**：1 个　**代码**：56 行

**做了什么**

把数据库表映射成 Java 类，一个实体类对应一张表，一个属性对应一个字段。
属性名用驼峰（`userId`），数据库字段名用下划线（`user_id`），
靠配置里的 `map-underscore-to-camel-case=true` 自动完成转换，不需要手写映射。

| 实体类 | 对应表 | 说明 |
|---|---|---|
| `User` | `user` | 用户，`role` 区分普通用户（0）和管理员（1） |
| `Category` | `category` | 文章分类 |
| `Tag` | `tag` | 文章标签 |
| `Article` | `article` | 文章，系统的核心表 |
| `ArticleTag` | `article_tag` | 多对多中间表 |
| `Comment` | `comment` | 评论 |

其中 `User`、`Category`、`Tag`、`Article`、`Comment` 五个类在实验一已随数据库设计
一并完成，本次补充的是 `ArticleTag`（`article_tag` 中间表的实体类）。

**关键设计：`ArticleTag` 为什么和别的实体不一样**

其他五张表都有自增主键 `xxx_id`，`article_tag` 没有 —— 它用的是
`(article_id, tag_id)` **联合主键**。这是因为它的作用是表达"哪篇文章有哪个标签"
这种两两对应关系，一行记录由两个外键共同确定，再加一个自增 ID 没有意义。

```java
public class ArticleTag {
    private Integer articleId;   // 联合主键之一
    private Integer tagId;       // 联合主键之二
}
```

联合主键还有一个额外好处：从数据库层面保证同一篇文章不会重复贴同一个标签 ——
重复插入会被主键冲突直接拒绝，不用靠代码去防。

### 第 2 次：DAO 层

**提交**：`8cec761`　**文件**：12 个（6 接口 + 6 XML）　**代码**：811 行

**做了什么**

为每张表建一个 Mapper 接口和一个同名 XML 文件。接口里只声明方法，
SQL 全部写在 XML 里，启动时由 MyBatis 动态生成实现类 —— 也就是说
**DAO 层没有一行手写的实现代码**。

每张表都有标准的增删改查，另加一些业务查询：

| Mapper | 额外方法 | 用途 |
|---|---|---|
| `UserMapper` | `selectByUsername` | 注册查重、登录 |
| `CategoryMapper` | `selectByName` | 分类名查重 |
| `TagMapper` | `selectByName` | 标签名查重 |
| `ArticleMapper` | `selectAll`、`increaseViewCount`、`countByCategoryId`、`countByUserId` | 列表页不查正文、浏览量自增、删除前的占用检查 |
| `ArticleTagMapper` | `selectTagsByArticleId`、`selectOne`、`deleteByArticleId`、`deleteByTagId`、`countByTagId` | 多对多关联的查询与清理 |
| `CommentMapper` | `selectByArticleId`、`selectByUserId`、`deleteByArticleId`、`deleteByParentId`、`deleteByUserId`、`countByArticleId` | 评论查询与级联清理 |

**四个实现要点**

1. **主键回填**：新增时用 `useGeneratedKeys="true" keyProperty="xxxId"`，
   把数据库生成的自增 ID 写回 Java 对象，否则插入完拿不到新记录的 ID。

   ```xml
   <insert id="insert" parameterType="Article" useGeneratedKeys="true" keyProperty="articleId">
       INSERT INTO article (title, content, user_id, category_id)
       VALUES (#{title}, #{content}, #{userId}, #{categoryId})
   </insert>
   ```

2. **时间字段不由 Java 传**：`create_time` 交给数据库默认值
   `DEFAULT CURRENT_TIMESTAMP`，`update_time` 靠 `ON UPDATE CURRENT_TIMESTAMP` 自动更新。
   这样多个入口写数据时，时间口径是统一的。

3. **浏览量用 SQL 自增**：写成 `view_count = view_count + 1`，
   而不是"先查出来、加一、再写回"。后者在两个人同时访问时会互相覆盖，丢掉一次计数。

4. **多对多靠 JOIN**：查"某篇文章的标签"要连 `tag` 和 `article_tag` 两张表，
   返回的是 `Tag` 对象而不是 `ArticleTag` —— 页面要显示标签名，不是标签 ID。

   ```xml
   <select id="selectTagsByArticleId" resultType="Tag">
       SELECT t.tag_id,
              t.name
       FROM tag t
                INNER JOIN article_tag atg ON t.tag_id = atg.tag_id
       WHERE atg.article_id = #{articleId}
       ORDER BY t.tag_id ASC
   </select>

另外，`user` 是 MySQL 的保留字，SQL 里必须写成 `` `user` ``（反引号），
否则建表和查询都会报语法错误。

### 第 3 次：Service 层

**提交**：`8a62d69`　**文件**：11 个　**代码**：1063 行

**做了什么**

Controller 只负责收发请求，Mapper 只负责执行 SQL，**中间的判断全部集中在 Service 层**。
这样做的原因是：同一个规则不管从网页、手机 App 还是别的入口调进来，都必须一样，
放在 Service 层就只有一份。

新增 6 个文件（1 个异常类 + 5 个 Service 接口）和 5 个实现类：

| Service | 业务规则 |
|---|---|
| `UserService` | 注册时用户名必填且不能重复；登录失败统一提示"用户名或密码错误"（不区分是用户名不存在还是密码错，防止被人试探出已注册的用户名）；**返回给外层的对象一律把密码置为 null**；改资料时用户名要重新查重、不传密码则保留原密码；用户还有文章时不许删 |
| `CategoryService` | 分类名不能重复；分类下还有文章时拒绝删除 |
| `TagService` | 标签名不能重复；删除时先清 `article_tag` 关联再删标签 |
| `ArticleService` | 发表时校验标题非空、作者存在、分类存在（分类可以不填）；查详情时浏览量加一；删除时校验操作人必须是作者本人或管理员，并在一个事务里依次删评论 → 删标签关联 → 删文章 |
| `CommentService` | 发表时校验内容非空、用户存在、文章存在；删除时校验操作人必须是评论作者本人或管理员 |

**关键设计一：`BusinessException` 区分"业务错误"和"系统故障"**

用户输入不合法（比如分类重名）和程序出 bug（比如空指针）是两回事。
前者应该把原因原样告诉用户，后者不应该把堆栈暴露出去。
所以自定义了一个 `BusinessException`，凡是业务规则不通过就抛它，
由后面的全局异常处理器统一转成友好提示。

**关键设计二：`@Transactional` 用在"一次操作动多张表"的地方**

比如删文章要依次删评论、删标签关联、删文章本身。这三步必须是一个整体 ——
如果第一步成功后程序出错，事务会整体回滚，不会留下"评论删了但文章还在"的脏数据。

删除顺序也不是随便定的，由外键决定：`comment` 和 `article_tag` 都有外键指向
`article`，必须先删它们，最后才能删文章，反了会触发"外键约束失败"。

**关键设计三：权限判断写成私有方法复用**

删文章、删评论、改标签三处用的规则完全一样（作者本人或管理员），
抽成一个私有方法：

```java
private void checkPermission(Integer operatorId, Integer ownerId, String action) {
    if (operatorId == null) {
        throw new BusinessException("缺少操作人ID");
    }
    User operator = userMapper.selectById(operatorId);
    if (operator == null) {
        throw new BusinessException("操作人不存在：" + operatorId);
    }
    if (operatorId.equals(ownerId)) {                    // 情况一：本人
        return;
    }
    if (Integer.valueOf(1).equals(operator.getRole())) {  // 情况二：管理员
        return;
    }
    throw new BusinessException("没有权限" + action + "（只有作者本人和管理员可以操作）");
}
```

### 第 4 次：Service 层修正（新增后回查）

**提交**：`1bc02e8`　**文件**：3 个　**代码**：18 行

**问题**

用 curl 测接口时发现：新增文章/评论/用户成功后，返回的 JSON 里
`createTime` 是 `null`。

**原因**

`create_time` 的值是数据库自动填的，MyBatis 的 `useGeneratedKeys` 只会把
**自增主键**回填到 Java 对象上，数据库生成的其他字段值它拿不到。
所以插入完之后，手里这个对象的时间字段还是 `null`。

**解决**

插入之后按新 ID 回查一次再返回：

```java
articleMapper.insert(article);
return articleMapper.selectById(article.getArticleId());   // 回查，拿到时间等数据库填的值
```

多一次查询换来"接口返回的记录和数据库里的完全一致"，对调用方来说更省事 ——
不用再发一次请求去查刚插入的数据。

### 第 5 次：Controller 层

**提交**：`b28992d`　**文件**：6 个　**代码**：581 行

**做了什么**

5 个控制器对应 5 个业务模块，一共 28 个 REST 接口，全部返回统一格式：

```json
{"code": 200, "msg": "操作成功", "data": {...}}
```

| 方式 | 路径 | 说明 |
|---|---|---|
| POST | `/user/register`　`/user/login` | 注册、登录 |
| GET | `/user/list`　`/user/{id}` | 用户列表、详情 |
| PUT / DELETE | `/user/update`　`/user/{id}` | 修改、删除 |
| GET | `/category/list`　`/category/{id}` | 分类列表、详情 |
| POST / PUT / DELETE | `/category/add`　`/category/update`　`/category/{id}` | 分类增改删 |
| GET | `/tag/list`　`/tag/{id}` | 标签列表、详情 |
| POST / PUT / DELETE | `/tag/add`　`/tag/update`　`/tag/{id}` | 标签增改删 |
| GET | `/article/list`　`/article/{id}` | 文章列表（不含正文）、详情（含正文，浏览量 +1） |
| POST / PUT / DELETE | `/article/add`　`/article/update`　`/article/{id}?operatorId=` | 文章增改删 |
| GET / POST / DELETE | `/article/{id}/tags`　`/article/{id}/tag/{tagId}?operatorId=` | 文章标签的查询、贴、取消 |
| GET | `/comment/article/{articleId}`　`/comment/user/{userId}` | 评论查询 |
| POST / DELETE | `/comment/add`　`/comment/{id}?operatorId=` | 发表、删除评论 |

**关于 `operatorId`**

删文章、删评论、改标签这三个操作需要判断"现在是谁在操作"。
本实验还没做登录会话，所以由调用方在 URL 上把当前用户 ID 带过来，
比如 `DELETE /article/1?operatorId=2`。等以后接了登录功能，
这个参数从会话里取，接口本身不用改。

**关键设计：`@RestControllerAdvice` 全局异常处理**

`GlobalExceptionHandler` 统一接住所有控制器抛出的异常，分三类处理：

| 异常类型 | 处理方式 |
|---|---|
| `BusinessException` | 返回具体原因，如"分类名称已存在：学习笔记" |
| `HttpMessageNotReadableException` | 请求体 JSON 格式错误，提示"请求体不是合法的 JSON" |
| 其他未知异常 | 堆栈打印到控制台，对外只返回"服务器内部错误"，不泄露内部细节 |

因为有了这个处理器，5 个 Controller 里**没有一处 try-catch**，
每个方法的代码就是"调 Service，把结果包装成统一格式返回"。

**做了什么**

对 5 个 Service 实现类写单元测试，用 **JUnit 5 + Mockito**。

| 测试类 | 当时的用例数 |
|---|---|

**关键设计：不启动 Spring，不连数据库**

（`@InjectMocks` 自动注入），测试跑起来不到 1 秒：

```java
@ExtendWith(MockitoExtension.class)
class ArticleServiceImplTest {

    @Mock
    private ArticleMapper articleMapper;      // 假的 Mapper，不会真连数据库

    @Mock
    private UserMapper userMapper;

        when(articleMapper.selectById(1)).thenReturn(buildArticle(1, 1));  // 作者是 1 号
        when(userMapper.selectById(2)).thenReturn(buildUser(2, 0));       // 操作人 2 号是普通用户

                () -> articleService.delete(1, 2));

        assertTrue(ex.getMessage().contains("没有权限"));

        verify(commentMapper, never()).deleteByArticleId(anyInt());
        verify(articleTagMapper, never()).deleteByArticleId(anyInt());
        verify(articleMapper, never()).deleteById(anyInt());
    }

```

**两个测试技巧**

1. **验证"不该发生的事"**：光断言"抛没抛异常"不够，还要用
   `verify(mapper, never()).xxx()` 确认校验没过时数据库操作确实一次都没执行。
   否则可能出现"既跑了删除、又抛了异常"这种看起来对、实际有副作用的情况。

2. **验证调用顺序**：删文章要动三张表，顺序反了会触发外键错误。
   用 Mockito 的 `InOrder` 断言这个顺序：

### 第 8 次：评论支持回复

**提交**：`7238745`　**文件**：13 个　**代码**：419 行

**问题**

原来的评论都平铺在文章下面，只能"对文章评论"，不能"回复某一条评论"。
数据库里也没有"回复谁"这个概念。

**数据库变更**

`comment` 表加两个字段和两条外键：

```sql
ALTER TABLE `comment`
  ADD COLUMN `parent_id` INT NULL COMMENT '所属顶层评论ID，NULL表示这条本身就是顶层评论' AFTER `article_id`,
  ADD COLUMN `reply_to_user_id` INT NULL COMMENT '被回复人的用户ID，NULL表示直接对文章评论' AFTER `parent_id`,
  ADD CONSTRAINT fk_comment_parent     FOREIGN KEY (`parent_id`)        REFERENCES `comment`(`comment_id`),
  ADD CONSTRAINT fk_comment_reply_user FOREIGN KEY (`reply_to_user_id`) REFERENCES `user`(`user_id`);
```

**为什么是两个字段而不是一个**

- `parent_id` 决定这条评论**挂在哪里**（树的形状），它只指向**顶层**评论。
- `reply_to_user_id` 决定这条评论**在对谁说话**（页面显示"回复 @某某"）。

如果只存"我回复的那条评论"（一个字段），会出现两个问题：
一是 A 回复 B、B 又回复 A 会形成越来越深的链条，删一条要递归找所有子孙；
二是页面分不清谁在跟谁说话。

**关键设计：评论压成两层，归一化在写入时做一次**

规则是：回复只有两层 —— 顶层评论，和它下面的回复。回复"一条回复"时，
新评论会被**提到同一个顶层评论下**。归一化逻辑写在 `CommentServiceImpl.add` 里：

```
前端传来 parentId（想回复哪条评论）
  ├─ 为 null → 顶层评论，直接存
  └─ 不为 null
       ├─ 查出被回复的评论，不存在 → 报错
       ├─ 它必须和新评论属于同一篇文章 → 否则报错
       ├─ 它本身也是回复 → 把新评论的 parentId 改成它的 parentId（提到顶层）
       └─ replyToUserId = 被回复那条评论的作者
```

这么做换来两个好处：

- **查**一棵评论树只要一次查询，页面按 `parentId` 分组就拼成两层，不用递归；
- **删**顶层评论只要一句 `WHERE parent_id = ?` 就清干净，不用递归找子孙。

代价只是写入时多一次判断，把复杂度挡在了一个地方。

**安全考虑：被回复人由后端推导，不接受前端传入**

`reply_to_user_id` 如果照抄前端传的值，谁都能构造一个请求伪造成"某某回复了你"。
所以 Service 里先把前端传的清掉，再根据 `parent_id` 指向的那条评论的作者推导出来：

```java
comment.setReplyToUserId(null);          // 先清掉前端可能传来的值
if (comment.getParentId() != null) {
    Comment parent = commentMapper.selectById(comment.getParentId());
    ...
    comment.setReplyToUserId(parent.getUserId());   // 由后端推导出真正的被回复人
}
```

**删除的级联**

删顶层评论时，它下面的回复要一起删掉，否则会留下没有归属的孤儿回复。
顺序不能反：回复的 `parent_id` 有外键指向顶层评论，先删顶层评论会被外键拦住。

```java
commentMapper.deleteByParentId(commentId);   // 先删它下面的回复
commentMapper.deleteById(commentId);         // 再删它自己
```

方法加了 `@Transactional`，保证这两步是一个整体。

**页面构成**

| 区域 | 内容 |
|---|---|
| 顶部 | 身份切换下拉框（切换后，发文章/评论的作者、删除和改标签的操作人都会变成这个人） |

**关键设计：所有请求走同一个 `api()` 函数**

```javascript
async function api(method, path, body) {
    addLog(`${method} ${path}`, 'req');                    // 记请求日志
    const response = await fetch(path, options);
    const result = await response.json();
    addLog('  → ' + JSON.stringify(result), result.code === 200 ? 'ok' : 'err');
    if (result.code !== 200) {
        toast(result.msg, 'err');                          // 统一弹提示
        throw new Error(result.msg);
    }
    return result.data;                                    // 调用方只关心成功的数据
}
```

好处是：调用方不用每次都写重复的判断和提示；右侧日志把"请求了什么、返回了什么"
完整记下来，看日志就能理解接口的行为，也方便演示权限拦截。

**页面也做了 XSS 防护**

用户输入的内容（标题、正文、评论）直接拼进 HTML 会有风险 ——
万一有人发的内容里带 `<script>` 标签，浏览器会当成代码执行。
所有拼进页面的用户输入都经过 `escapeHtml()` 转义。

## 四、回顾：这次开发中值得记下的几个点

1. **`create_time` 是 `null`**（第 4 次提交）：MyBatis 的 `useGeneratedKeys`
   只回填自增主键，数据库自动生成的其他字段要回查才能拿到。

2. **删除顺序由外键决定**：先删"子表"再删"父表"，
   所以是"评论 → 标签关联 → 文章"、"回复 → 顶层评论"。顺序反了报的是
   "外键约束失败"，报错信息不会告诉你顺序错了，只能自己想明白表之间的关系。

3. **权限校验容易被漏掉**：实验要求里没写"标签要有权限"，是实际点着走流程
   才发现的。这说明光跑通正常流程不够，还要主动试试"不该成功的事会不会成功" ——
   这也正是单元测试里要写 `verify(mock, never())` 的原因。

4. **归一化放在写入时做一次**：评论回复如果不做归一化，读取和删除都要递归。
   把复杂度挡在写入这一个点上，后面所有操作都变简单。
