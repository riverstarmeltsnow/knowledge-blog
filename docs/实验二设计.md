## 二、Entity 层：6 张表 6 个实体类

一个实体类对应一张表，一个属性对应一个字段。属性名用驼峰（`userId`），
数据库字段名用下划线（`user_id`），靠 `application.properties` 里的
`map-underscore-to-camel-case=true` 自动转换。

| 实体类 | 对应表 | 说明 |
|---|---|---|
| `User` | `user` | 用户，`role` 字段区分普通用户（0）和管理员（1） |
| `Category` | `category` | 文章分类，与文章是 1:N |
| `Tag` | `tag` | 文章标签，与文章是 M:N |
| `Article` | `article` | 文章，系统的核心表 |
| `ArticleTag` | `article_tag` | 中间表，联合主键 `(articleId, tagId)`，无自增ID |
| `Comment` | `comment` | 评论，关联用户、文章，还自关联本表（`parentId` 表示回复哪条顶层评论） |

## 三、DAO 层：6 个 Mapper 接口 + 6 个 XML

接口里只声明方法，SQL 写在同名的 XML 里，启动时由 MyBatis 生成实现类。
每张表都有标准的增删改查，另加一些业务查询。

| Mapper | 标准方法 | 额外方法 |
|---|---|---|
| `UserMapper` | selectAll / selectById / insert / update / deleteById | selectByUsername（注册查重、登录） |
| `CategoryMapper` | selectAll / selectById / insert / update / deleteById | selectByName（名称查重） |
| `TagMapper` | selectAll / selectById / insert / update / deleteById | selectByName（名称查重） |
| `ArticleMapper` | selectById / insert / update / deleteById | selectAll（列表不查正文）、increaseViewCount、countByCategoryId、countByUserId |
| `ArticleTagMapper` | insert / delete | selectTagsByArticleId（JOIN 标签表）、selectOne、deleteByArticleId、deleteByTagId、countByTagId |
| `CommentMapper` | selectById / insert / deleteById | selectByArticleId、selectByUserId、deleteByArticleId、deleteByParentId、deleteByUserId、countByArticleId |

**几个实现要点**：

1. **主键回填**：新增时用 `useGeneratedKeys="true" keyProperty="xxxId"`，
   把数据库生成的自增ID写回 Java 对象，否则新增完拿不到新ID。
2. **时间字段不传**：`create_time` 交给数据库默认值，`update_time` 靠
   `ON UPDATE CURRENT_TIMESTAMP` 自动更新，Java 代码不参与。
3. **浏览量用 SQL 自增**：`view_count = view_count + 1`，而不是"查出来加一再写回"，
   避免两个人同时访问时互相覆盖。
4. **多对多靠 JOIN**：查"某篇文章的标签"要连 `tag` 和 `article_tag` 两张表，
   返回的是 `Tag` 而不是 `ArticleTag`（页面要显示标签名，不是标签ID）。
5. **`user` 是关键字**：SQL 里要写成 `` `user` ``（反引号）。

## 四、Service 层：业务规则集中在这里

Controller 只负责收发，Mapper 只负责执行 SQL，中间的判断全在 Service 层。

| Service | 业务规则 |
|---|---|
| `UserService` | 注册时用户名必填且不能重复；登录失败统一提示"用户名或密码错误"（不区分是用户名不存在还是密码错，防止被人试探出已注册的用户名）；**返回给外层的对象一律把密码置为 null**；改资料时用户名要重新查重、不传密码则保留原密码；用户还有文章时不许删（评论则连带删除） |
| `CategoryService` | 分类名不能重复；分类下还有文章时拒绝删除（替数据库外键提前把关，给出中文提示） |
| `TagService` | 标签名不能重复；删除时先清 `article_tag` 关联再删标签（`@Transactional`） |
| `ArticleService` | 发表时校验标题非空、作者存在、分类存在（分类可以不填）；查详情时浏览量加一；删除时校验操作人必须是作者本人或管理员，并在一个事务里依次删评论 → 删标签关联 → 删文章；**贴标签和取消标签同样校验操作人必须是作者本人或管理员**（标签属于文章内容的一部分，谁能改文章谁才能改它的标签），且不能重复贴 |
| `CommentService` | 发表时校验内容非空、用户存在、文章存在；**回复时校验被回复的评论存在、且属于同一篇文章**；删除时校验操作人必须是评论作者本人或管理员，**删顶层评论时连带删掉它下面的所有回复** |

**事务的用法**：凡是"一次操作要动多张表"的地方都加了 `@Transactional`，
比如删文章要动三张表。加了它之后，中途出错会整体回滚，
不会留下"评论删了但文章还在"的脏数据。

**权限用 `role` 字段判断**：`role = 1` 是管理员，能操作任何人的内容；
否则只能操作自己的。判断逻辑写成 Service 的私有方法 `checkPermission`，
文章、评论、标签三处规则一致（都是"作者本人或管理员"）。

**评论回复的归一化**：评论表用自联系字段 `parent_id` 表达回复，但把层级
**压成两层**，归一化在 `CommentServiceImpl.add` 里一次做完：

```
前端传来 parentId（想回复哪条评论）
  ├─ 为 null → 顶层评论，直接存
  └─ 不为 null
       ├─ 查出被回复的评论，不存在 → 报错
       ├─ 它必须和新评论属于同一篇文章 → 否则报错
       ├─ 它本身也是回复 → 把新评论的 parentId 改成它的 parentId（提到顶层）
       └─ replyToUserId = 被回复那条评论的作者
```

这样换来两个好处：**查**一棵评论树只要一次查询，页面按 `parentId` 分组就拼出来了；
**删**顶层评论只要 `WHERE parent_id = ?` 一句就清干净，不用递归找子孙。

其中 `replyToUserId` 由后端推导，**不接受前端传入**——
否则谁都能构造一个请求伪造成"某某回复了你"。测试里专门有一条用例覆盖这点。

## 五、Controller 层：REST 接口清单

所有接口返回统一格式：`{"code":200/500, "msg":"提示", "data":...}`。

| 方式 | 路径 | 说明 |
|---|---|---|
| POST | `/user/register` | 注册 |
| POST | `/user/login?username=&password=` | 登录 |
| GET | `/user/list` | 用户列表 |
| GET | `/user/{id}` | 用户详情 |
| PUT | `/user/update` | 修改资料 |
| DELETE | `/user/{id}` | 删除用户 |
| GET | `/category/list` | 分类列表 |
| GET | `/category/{id}` | 分类详情 |
| POST | `/category/add` | 新增分类 |
| PUT | `/category/update` | 修改分类 |
| DELETE | `/category/{id}` | 删除分类 |
| GET | `/tag/list` | 标签列表 |
| GET | `/tag/{id}` | 标签详情 |
| POST | `/tag/add` | 新增标签 |
| PUT | `/tag/update` | 修改标签 |
| DELETE | `/tag/{id}` | 删除标签 |
| GET | `/article/list` | 文章列表（不含正文） |
| GET | `/article/{id}` | 文章详情（含正文，浏览量 +1） |
| POST | `/article/add` | 发表文章 |
| PUT | `/article/update` | 修改文章 |
| DELETE | `/article/{id}?operatorId=` | 删除文章（级联删评论和标签关联） |
| GET | `/article/{id}/tags` | 查这篇文章的标签 |
| POST | `/article/{id}/tag/{tagId}?operatorId=` | 给文章贴标签（仅作者本人和管理员） |
| DELETE | `/article/{id}/tag/{tagId}?operatorId=` | 取消标签（仅作者本人和管理员） |
| GET | `/comment/article/{articleId}` | 某篇文章的评论（平铺返回，按 `parentId` 分组成两层） |
| GET | `/comment/user/{userId}` | 某个用户的评论 |
| POST | `/comment/add` | 发表评论；请求体带 `parentId` 时就是回复某条评论 |
| DELETE | `/comment/{id}?operatorId=` | 删除评论（删顶层评论会连带删它的回复） |

**关于 `operatorId`**：本实验还没做登录会话，所以"当前是谁在操作"由调用方
在 URL 上带过来。等以后接了登录功能，这个参数从会话里取，接口不用改。

**全局异常处理**：`GlobalExceptionHandler` 用 `@RestControllerAdvice` 统一接住
异常 —— 业务异常返回具体原因（如"分类名称已存在：学习笔记"），
请求体 JSON 格式错误给出明确提示，其他未知异常打印堆栈到控制台、
对外只返回"服务器内部错误"。有了它，5 个 Controller 里没有一处 try-catch。

## 六、单元测试

测试放在 `src/test/java/cuit/mygit/service/`，用 **JUnit 5 + Mockito**。
被测对象是 Service 实现类，它依赖的 Mapper 全部用 `@Mock` 造假的
（`@InjectMocks` 自动注入），所以**不启动 Spring、不连数据库**，
跑一遍不到 1 秒。

| 测试类 | 用例数 | 覆盖内容 |
|---|---|---|
| `UserServiceImplTest` | 10 | 注册成功 / 用户名重复 / 用户名密码为空 / 登录成功 / 密码错误 / 用户不存在 / 返回结果不含密码 / 有文章时不许删 / 删用户连带删评论 |
| `ArticleServiceImplTest` | 20 | 列表查询 / 详情浏览量+1 / 文章不存在 / 标题为空 / 作者不存在 / 分类不存在 / 不填分类也能发 / 非作者删除被拒 / 作者本人删除的级联顺序 / 管理员删除 / 贴标签重复 / 标签不存在 / 取消未贴过的标签 / **非作者改标签被拒 / 管理员可以改别人的标签** |
| `CategoryServiceImplTest` | 9 | 名称重复 / 名称为空 / 分类下有文章拒绝删除 / 只改描述不该判重名 / 改成别人的名字被拒 |
| `TagServiceImplTest` | 5 | 名称重复 / 删除时先清关联再删标签（验证调用顺序）/ 标签不存在 |
| `CommentServiceImplTest` | 19 | 内容为空 / 评论人不存在 / 文章不存在 / 非作者删除被拒 / 作者本人删除 / 管理员删除 / 操作人不存在 / **回复顶层评论（被回复人由后端推出）/ 回复一条回复被提到顶层 / 前端伪造 replyToUserId 被忽略 / 顶层评论不带 replyToUserId / 被回复的评论不存在 / 跨文章回复被拒 / 删顶层评论时先删回复再删自己（验证顺序）** |
| 合计 | **63** | 加上 `MygitApplicationTests` 的启动冒烟测试，共 64 个 |

**两个测试技巧**：

1. **验证"不该发生的事"**：光断言抛没抛异常不够，还要用
   `verify(mapper, never()).deleteById(anyInt())` 确认校验没过时
   数据库操作确实一次都没执行。
2. **验证调用顺序**：删文章和删标签都要动多张表，顺序反了会触发数据库外键错误。
   用 Mockito 的 `InOrder` 可以断言这个顺序，比如：
   先 `commentMapper.deleteByArticleId()`，再 `articleTagMapper.deleteByArticleId()`，
   最后才 `articleMapper.deleteById()`。

## 七、运行与验证

```bash
# 1. 跑单元测试（不需要数据库，应该全部通过）
mvn test

# 2. 启动应用（需要本地 MySQL 已建库并导入 docs/schema.sql + docs/test_data.sql）
mvn spring-boot:run

# 3. 浏览器或 curl 验证接口
curl http://localhost:8080/article/list
curl http://localhost:8080/article/1
curl http://localhost:8080/article/1/tags
curl -X POST "http://localhost:8080/user/login?username=hexin&password=123456"
curl -X DELETE "http://localhost:8080/article/1?operatorId=2"   # 非作者，应被拒绝
```

> **用 curl 测中文参数时注意**：Windows 的 Git Bash 会把命令行里的中文
> 按 GBK 编码传给 `curl.exe`，服务端按 UTF-8 解析就会失败。
> 解决办法是把 JSON 先写进文件，再用 `--data-binary @文件名` 发送。
