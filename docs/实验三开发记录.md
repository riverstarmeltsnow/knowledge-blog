## 二、逐次提交说明

### 第 1 次：参数校验

**提交**：`74196b0`　**文件**：13 个　**代码**：+373 −30

**做了什么**

在这之前，一个请求要在经历了 Controller → Service 之后才可能被判断出
"参数不对"。这有两个问题：一是判断分散在各个 Service 里，同一个规则
换个入口就得重写一遍；二是提示往往不够具体。

这次把"参数本身合不合法"这一层判断提到了进 Controller 之前，靠的是
Jakarta Bean Validation（Spring Boot 内置支持，只需加一个依赖）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

然后在实体类的字段上写规则：

```java
@NotBlank(message = "文章标题不能为空", groups = ValidGroup.Create.class)
@Size(max = 200, message = "文章标题不能超过 200 个字符", groups = ValidGroup.Create.class)
private String title;
```

最后在 Controller 的参数上加 `@Validated`，校验不通过就直接返回错误，
根本进不到 Service：

```java
@PostMapping("/add")
public Result<Article> add(
        @Validated(ValidGroup.Create.class) @RequestBody Article article) {
```

**关键设计一：为什么需要"校验分组"**

同一个实体类要应付两种场景，规则却不一样：

| 字段 | 新增时 | 修改时 |
|---|---|---|
| `articleId` | 没有（由数据库生成，提交时还不存在） | 必填（不填就不知道改哪一篇） |
| `username`、`password` | 必填（注册） | 可以不传（表示保留原值，只改邮箱也得能提交） |

一套规则没法同时满足两边，所以定义两个空的接口当作"标签"：

```java
public interface ValidGroup {
    /** 新增时用的校验规则 */
    interface Create {
    }

    /** 修改时用的校验规则 */
    interface Update {
    }
}
```

注解上写 `groups = ValidGroup.Create.class`，Controller 上写
`@Validated(ValidGroup.Update.class)`，这次请求就只检查属于 Update 分组的规则。

**这里有个容易踩的坑**：`groups` 不写的注解属于 **Default 分组**，
而 `@Validated(ValidGroup.Create.class)` 只检查 Create 分组 ——
**Default 分组的注解在任何一个分组下都不会被检查**。也就是说，
写注解时忘了写 `groups`，这条规则就等于没写。所有注解都显式带上
分组，就是为了避开这个坑。

**关键设计二：长度上限对齐数据库**

`@Size` 的上限不是随手定的，是先去 `schema.sql` 里查出每张表每个字段的
真实长度再写：

| 字段 | 数据库定义 | 注解 |
|---|---|---|
| `article.title` | `VARCHAR(200)` | `@Size(max = 200)` |
| `user.username` | `VARCHAR(50)` | `@Size(max = 50)` |
| `comment.content` | `VARCHAR(500)` | `@Size(max = 500)` |

这样校验拦下来的，正好就是数据库会拒绝的那些，不会出现"校验放行了、
写库时却报字段太长"的情况。

**有一个字段故意没写 `@Size`**：`article.content` 在数据库里是 `LONGTEXT`
（能存 4GB），在 Java 这边给它编一个长度上限反而是错的 —— 会拒绝掉
数据库本来能存下的正文。所以它的注解只有 `@NotBlank`。

**关键设计三：评论只有 Create 分组，没有 Update**

```java
@NotBlank(message = "评论内容不能为空", groups = ValidGroup.Create.class)
private String content;
```

评论发出去就固定了，写错了只能删掉重发 —— 整个系统里只有评论是
完整的增删查、没有改。所以它的校验注解全部只属于 Create 分组，
`CommentController` 里也没有 update 接口。这是有意设计的，
不是漏做了。

**关键设计四：一次把所有错误都说出来**

一个请求可能好几个字段同时不合法（标题空着、正文也空着）。
默认行为是抛异常时只说第一条，用户改完再提交又撞出下一条，
来回好几轮才能提交成功。所以校验失败的处理器把所有提示收集起来
一起去重、再用中文分号连起来：

```java
String message = e.getBindingResult().getFieldErrors().stream()
        .map(error -> error.getDefaultMessage() == null
                ? error.getField() + " 不合法"
                : error.getDefaultMessage())
        .distinct()
        .collect(Collectors.joining("；"));
```

返回的样子是 `"文章正文不能为空；文章标题不能为空"`。

**异常处理器补了四类**

`GlobalExceptionHandler` 原来只有业务异常、JSON 格式错误和兜底三种。
这次把调用方最容易撞上的四类参数错误都单独处理了，各给一句能看懂的提示：

| 异常 | 什么情况下会撞上 | 返回的提示 |
|---|---|---|
| `MethodArgumentNotValidException` | 校验注解没通过 | 注解里写的中文提示，多条拼起来 |
| `MissingServletRequestParameterException` | 少传了 URL 上的参数 | "缺少必需的参数：operatorId" |
| `MethodArgumentTypeMismatchException` | `/article/abc` —— ID 位置写了非数字 | "参数格式不正确：id" |
| `InvalidParameterException` | URL 里的中文编码不对（见下文"三、遇到的问题"） | "请求参数解码失败：URL 里的中文等特殊字符请使用 UTF-8 编码" |

顺带把兜底的 `printStackTrace()` 换成了 `log.error()` —— 前者只往控制台一扔，
程序一重启就没了；日志框架的输出带时间戳和线程名，也能配置写到文件里。

**`Result` 加了一个自定义状态码的重载**

```java
public static <T> Result<T> error(String msg) {
    return error(500, msg);
}

public static <T> Result<T> error(int code, String msg) {
    ...
}
```

原来的 `error(String)` 把状态码写死成 500。加这个重载是为了"资源不存在"
这种情况 —— 找不到文件跟"服务器出错了"是两码事，硬塞进 500 会误导人。

### 第 2 次：分页、搜索与筛选

**提交**：`5c99f9c`　**文件**：7 个　**代码**：+748 −2

**做了什么**

原来的 `/article/list` 是"一次查全部"，这次在它之外新增了 5 个查询接口，
`/article/list` 本身保留不动（测试台页面还在用它）：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/article/page?page=1&size=10` | 分页 |
| GET | `/article/search?keyword=MySQL` | 按标题关键字搜索 |
| GET | `/article/author/{userId}` | 某个作者的全部文章 |
| GET | `/article/category/{categoryId}` | 某个分类下的文章 |
| GET | `/article/tag/{tagId}` | 贴了某个标签的文章 |

**关键设计一：`PageResult` 把分页该有的东西一次给全**

分页查询如果只返回"这一页的数据"，前端就不知道总共多少页、有没有下一页，
只能再发一次请求问总数。所以专门做了一个返回结构，一次把所有派生信息算好：

```java
public PageResult(List<T> list, long total, int page, int size) {
    this.list = list;
    this.total = total;
    this.page = page;
    this.size = size;
    // 向上取整求总页数
    this.totalPages = size <= 0 ? 0 : (int) ((total + size - 1) / size);
    this.hasNext = page < totalPages;
    this.hasPrev = page > 1;
}
```

**总页数为什么要写成 `(total + size - 1) / size`**：Java 的整数除法是向下取整的，
直接写 `total / size`，87 条数据每页 10 条会算出 8 页，可实际上第 9 页还有 7 条 ——
页码条会少画一页，最后一页的数据用户根本点不到。加 `size - 1` 再除，
就把向下取整变成了向上取整。

**关键设计二：`LIMIT` 的偏移量不是页码**

```xml
<select id="selectPage" resultType="Article">
    SELECT article_id, title, user_id, category_id, view_count, create_time, update_time
    FROM article
    ORDER BY create_time DESC
    LIMIT #{offset}, #{size}
</select>
```

MySQL 的 `LIMIT a, b` 意思是"跳过前 a 条，取 b 条"，a 是**偏移量**不是页码。
第 3 页每页 10 条要跳过的是前 20 条，所以：

```java
long offset = (long) (safePage - 1) * safeSize;
```

**先转 `long` 再乘**是为了防溢出：如果按 `int` 算，一个特别大的页码
（比如 `page=214748365`）乘上 size 会超出 `int` 的范围，得到一个负数，
负的偏移量传给 MySQL 会直接报语法错误。转成 64 位能算到 9×10¹⁸，
而这个项目里文章 ID 是 `int`，最多也就二十多亿条，够用了；
即便如此还是加了一道保险，偏移量大到 `int` 装不下时直接返回空页。

**关键设计三：分页参数要做防御，不能直接信**

```java
private static final int MAX_PAGE_SIZE = 50;

int safePage = Math.max(page, 1);                          // page=0 或负数 → 纠正成第 1 页
int safeSize = Math.min(Math.max(size, 1), MAX_PAGE_SIZE); // size 限制在 1~50
```

- `page=0`、`page=-5` 这种，按第 1 页处理，不用报错 —— 语义上它们只是"越界了"，
  返回第一页比返回错误更有用。
- `size` 上限设成 50：这个接口是公开的，不设上限的话，
  有人写个 `size=999999` 就能一次把整张表拖走。默认值给的是 10。

**关键设计四：精确路径必须写在路径变量前面**

`/article/search` 和 `/article/page` 都是"一段固定文字"，而 `/article/{id}`
能匹配 `/article/` 底下的任意一段 —— 包括匹配上 `search` 和 `page`。
如果 `/{id}` 排在前面，访问 `/article/search` 时 Spring 会先把 `search`
当成文章 ID 去转整数，然后失败。

照理说 Spring Boot 3 以后用的路径匹配器会优先选"更具体"的那个，
所以顺序写反了多半也能正常工作。但依赖这个规则容易踩坑 ——
现在谁也不知道以后会不会改回去。所以老老实实把 5 个精确路径写在
`/{id}` 前面，并在代码里留了一段注释说明原因。

**关键设计五：按标签查是"反向"查**

其他几个筛选接口查的都是 `article` 表自己的字段，按标签查不行 ——
"文章有哪些标签"这个信息存在 `article_tag` 中间表里，得连一次表：

```xml
<select id="selectByTagId" resultType="Article">
    SELECT a.article_id, a.title, a.user_id, a.category_id,
           a.view_count, a.create_time, a.update_time
    FROM article a
             INNER JOIN article_tag atg ON a.article_id = atg.article_id
    WHERE atg.tag_id = #{tagId}
    ORDER BY a.create_time DESC
</select>
```

这和实验二就有的 `GET /article/{id}/tags` 正好是反过来的两条路：
那个是"这篇文章有哪些标签"，这个是"这个标签被哪些文章贴了"。

**关键设计六：模糊搜索要防注入**

搜索是按标题模糊匹配，SQL 长这样：

```xml
<select id="selectByTitle" resultType="Article">
    ... WHERE title LIKE CONCAT('%', #{keyword}, '%') ...
</select>
```

用 `CONCAT` 在 SQL 里拼通配符，而不是在 Java 里拼成 `"%"+keyword+"%"`
当成一个完整字符串传进去。因为 `#{keyword}` 是**参数占位符**，MyBatis 会用
`PreparedStatement` 的 `?` 传值，数据库把它当**数据**处理；
而如果拼成字符串用 `${}`，数据库会把它当 **SQL 语句的一部分**去解析，
搜索框里输入一段 SQL 片段就能改变查询的语义。

**关键设计七：筛选接口不校验"这个分类存不存在"**

同样是查，删除接口要校验"分类必须存在"，筛选接口却不校验。
这不是偷懒，是语义不同：

- 删除是**有副作用**的操作，说"删除分类 999"就得分清楚是删成功了
  还是这个分类压根不存在，必须报错；
- 筛选查询**没有副作用**，"分类 999 下的文章"这个问题的正确答案
  就是"一篇都没有"，返回空列表是准确的回答，不是错误。

所以 `listByCategoryId` 这类方法里只判断参数非空，查到什么返回什么。

**关键设计八：Service 层不参与"分页在哪一页"的计算**

`ArticleServiceImpl.page` 只做三件事：纠正参数、查总数、查这一页。
它不缓存、不记状态，每次调用都重新查一遍总数。因为文章可能随时在增减，
把总页数缓存起来反而会出现"页码条上有第 3 页，点进去是空的"的情况。

**测试补了 14 个用例**

`ArticleServiceImplTest` 从 20 个加到 34 个，覆盖的都是容易算错的地方：

| 用例 | 验证什么 |
|---|---|
| 第 3 页每页 10 条 | 传给 Mapper 的 offset 是 20 而不是 3 |
| 87 条每页 10 条 | 总页数是 9 而不是 8 |
| 最后一页 | `hasNext` 为 false |
| `size=1000` | 被截断成 50 |
| `page=0`、`page=-1` | 纠正成第 1 页 |
| 偏移量超出 int 范围 | 直接返回空页，不查数据库 |

### 第 3 次：博客前台页面

**提交**：`2e5d8d9`　**文件**：6 个　**代码**：3377 行

**做了什么**

新增 4 个页面和 2 个公共文件，都放在 `src/main/resources/static/` 下，
Spring Boot 启动后自动发布，不需要装 Node.js、不需要打包：

| 文件 | 页面 |
|---|---|
| `index.html` | 首页 —— 文章卡片列表、搜索、翻页 |
| `post.html` | 文章详情 —— 正文、标签、评论区（含回复） |
| `browse.html` | 分类与标签浏览 —— 左栏选择，右栏出文章 |
| `manage.html` | 管理后台 —— 文章/分类/标签/用户四个页签的增删改查 |
| `css/style.css` | 全部样式 |
| `js/common.js` | 各页面共用的工具函数 |

**为什么用原生 HTML + JS，不引框架**

这个项目是数据库课的实验，重点在后端的分层和数据。引一个前端框架
就得多一套 Node.js 环境和构建流程，老师拿到代码还得先 `npm install`
才能跑起来 —— 这对一个 Java 项目来说是额外的负担。

原生 JS 的代价是有些事要自己做（比如把 HTML 字符串拼起来、自己写分页条），
但换来的是"启动 Spring Boot 就能打开看"，零配置。

**页面配色特意和 `test.html` 分开**

`test.html` 是给自己测接口用的工具页，配色是蓝灰（`#2563eb`）。
博客前台换成了一套"浅色阅读风"：米白底（`#faf9f7`）、紫罗兰主色
（`#6d28d9`）、标题用衬线字体。两个页面摆在一起一眼能看出
"哪个是给人读的、哪个是测接口的"。

**关键设计一：搜索状态放在 URL 里，不放在变量里**

首页有两种状态 —— 普通列表和搜索结果，靠地址栏上有没有 `keyword` 参数区分：

```
http://localhost:8080/index.html              普通列表，带页码条
http://localhost:8080/index.html?keyword=MySQL  搜索结果，不带页码条
```

这么做而不是用一个 JS 变量记着，换来两个好处：刷新页面搜索结果还在；
搜索结果的地址可以直接发给别人。

**关键设计二：列表页不显示标签，是为了躲开 N+1 请求**

首页每张卡片上如果显示标签，就得为**每一篇**文章单独请求一次
`/article/{id}/tags` —— 一页 8 篇文章就是 8 个额外请求。
标签是点进详情页才关心的信息，列表页不显示它，8 个请求就省下来了。

同理，"分类与标签"页要在每个分类后面显示"这个分类有几篇文章"。
如果给每个分类都发一次 `/article/category/{id}` 问个数，
页面上有 10 个分类就是 10 个请求。所以改成开头用 `/article/list`
把全部文章拉**一次**，在浏览器里数一数每个分类各有多少篇。

**标签云那边连这个都省了**：要知道某个标签下有几篇文章，
得先知道每篇文章贴了哪些标签，那就又变成"文章数 × 1"个请求了。
所以标签云不显示数量 —— 这是权衡之后的取舍，不是漏做了。

**关键设计三：回复框只有一个，点"回复"时把它挪过去**

文章详情页的评论区有两层：顶层评论和它下面的回复。每条评论底下都有个
"回复"按钮。最直觉的做法是每条评论各配一个输入框，但那样有两个问题：
页面上会躺着几十个隐藏的输入框；用户打字打一半改去回复别人，已经敲的字就没了。

所以做成"一个回复框到处挪" —— 它平时藏在页面底部，点某条评论的
"回复"时用 `appendChild` 整个搬进那条评论里：

```javascript
function startReply(commentId) {
    const target = document.getElementById('comment-' + commentId);
    const form = $('#replyForm');
    ...
    target.appendChild(form);   // 搬进去，已经输入的内容原样保留
}
```

**顺带踩到一个坑**：删评论后会重新渲染整个评论区，而重新渲染是用
`innerHTML` 整体替换的 —— 那个正挂在某条评论里的回复框会被一起销毁，
之后 `$('#replyForm')` 就变成 `null` 了，再点"回复"直接报错。
解决办法是在渲染前先把回复框拎回 `body` 藏好，渲染完再挂回去，
顺带把"刚才在回复谁"也恢复上，否则用户打字打到一半去删了条评论，输入就白打了。

**关键设计四：前端的权限判断只是"预判"，不是"把关"**

有些按钮只有作者本人或管理员该看到（删文章、删评论、改标签）。
前端存了当前选中的身份，据此决定按钮显不显示：

```javascript
function canTouch(ownerId) {
    const me = getMe();
    if (!me) return false;
    return me.userId === ownerId || me.role === 1;
}
```

但必须说清楚：**这只是为了让用户少点一次白点的按钮**。
身份存在浏览器的 localStorage 里，谁都能改；绕过页面直接调接口照样能发请求。
真正拦住越权的是后端 Service 里的 `checkPermission`
（实验二第 3 次提交写的）。前端判断不能当成安全措施。

**关键设计五：所有数据库里取出来的文字都要转义**

文章标题、正文、评论内容、用户名 —— 这些全是用户输入，
如果直接拼进 `innerHTML`，有人在标题里写 `<script>alert(1)</script>`，
浏览器就会把它当代码执行，这叫 XSS。

所以公共文件里有一个 `escapeHtml()`，所有拼进页面的文本都过一遍它：

```javascript
function escapeHtml(text) {
    if (text === null || text === undefined) return '';
    return String(text)
        .replace(/&/g, '&amp;')   // 必须放第一个，否则会把下面生成的 & 再转一次
        .replace(/</g, '&lt;')
        .replace(/>/g, '&gt;')
        .replace(/"/g, '&quot;')
        .replace(/'/g, '&#39;');
}
```

**关键设计六：卡片渲染抽到公共文件，避免两边各写一份**

首页和"分类与标签"页都要画文章卡片，样子完全一样。
如果两个页面各写一份 `cardHtml`，将来改样式得记住改两个地方，很容易漏一个。
所以放进 `common.js`：

```javascript
function articleCardHtml(post, users, categories) { ... }
```

`users` 和 `categories` 数组是从外面传进来的，而不是在这个函数里发请求 ——
否则画 8 张卡片就要发 8 次 `/user/list`。这是这个项目处理"字典表"的统一做法：
页面开头请求一次全量，之后从数组里找。

**管理后台把四个模块收在一个页面的页签里**

文章、分类、标签、用户各一个页签，各自一张表格。新增和编辑共用同一个弹窗，
由 JS 换上不同的表单 —— 四个模块各做一个弹窗的话，光 HTML 就要多写两百行。

数据这一层的做法是：**每次增删改成功后，把四个模块的数据全部重新拉一遍**。
不在本地数组里改一改就完事，是因为后端的删除是有牵连的 ——
删一个分类会牵连它的文章，删一篇文章会带走评论和标签关联。
本地改很容易漏掉这些连锁反应，显示出来的东西就跟数据库对不上了。
多一次请求换个"所见即所得"，划算。

**一个已知的副作用**：在管理后台点"编辑文章"，那篇文章的浏览量会 +1。
因为列表接口 `/article/list` 是不带正文的（列表页用不上，查出来白费流量），
编辑时必须单独调 `/article/{id}` 去取完整内容，而那个接口的副作用就是计数。
要消掉它得让后端再加一个"只读详情、不计数"的接口，
对这个实验来说没必要。代码里在调用处写了注释说明，免得以后有人以为见鬼了。

### 第 6 次：用 Thymeleaf 重做管理后台

**提交**：`d3b8712`　**文件**：11 个　**代码**：+1929 −5

实验三的六条要求里，最后一条是这么写的：

> 基于 Thymeleaf 框架完成前端页面设计，实现对数据的增、删、改、查等基本功能，提交代码仓库

前五次提交做完后回头对这条要求，发现对不上。第 3 次提交做的那个
`manage.html` 是一个纯静态页面：HTML 里只有一个空表格骨架，页面打开后
浏览器自己去发十几个 `fetch` 请求调后端接口，拿到 JSON 再往表格里填。
**服务器发出去的 HTML 里，一个字的内容都没有。**

这不叫"基于 Thymeleaf 完成前端页面设计"。Thymeleaf 的工作方式正相反：
在服务器上把数据填进模板、拼成完整的 HTML 再发出去，浏览器拿到即可显示。
从代码结构到运行方式都不一样，在那个静态页面上改是改不出来的，只能另做一套。

**保留 `manage.html`，两套并存**。它不是废代码 —— 前台那几个页面
（首页、文章详情、分类标签浏览）本来就是静态的、靠接口拿数据。
后台多留一套静态版本，正好能在报告里做对比：同样是"文章列表"这个页面，
两种做法下浏览器拿到的 HTML 差在哪儿。这个对比后来做成了一张图。

**新增的文件**：

| 文件 | 说明 |
|---|---|
| `web/AdminController.java` | 后台控制器，20 条路由，四个模块的增删改查 |
| `templates/admin/layout.html` | 公共片段：`<head>`、顶部导航、提示条 |
| `templates/admin/articles.html` | 文章列表 + 分页条 |
| `templates/admin/article-form.html` | 文章的新增和修改共用这一个模板 |
| `templates/admin/categories.html` | 分类管理 |
| `templates/admin/tags.html` | 标签管理 |
| `templates/admin/users.html` | 用户管理 |
| `static/css/admin.css` | 后台样式，类名统一加 `adm-` 前缀 |

改动的既有文件只有两个：`pom.xml` 加 Thymeleaf 依赖，
`GlobalExceptionHandler` 加一个限定范围的参数（原因见下面的第 1 个坑）。

**Service 层 5 个接口、5 个实现类，一行都没改。** 改动全部落在
Controller 和视图这两层 —— 这也是分层的好处：换一种前端做法，
底下那层不用动。

**踩到的四个坑**：

1. **全局异常处理器会把页面错误变成一屏 JSON**。`GlobalExceptionHandler`
   上的 `@RestControllerAdvice` 是给接口用的 —— 它返回的东西会被转成 JSON。
   后台页面是 `@Controller` 渲染 HTML，一旦模板渲染出错，异常被它接走，
   用户看到的就是一屏 JSON 而不是错误页面。加
   `basePackages = "cuit.mygit.controller"` 把范围收到接口那一侧，
   `web` 包里的后台控制器就不受影响了。

2. **表单校验少了 `BindingResult` 会直接抛异常**。控制器方法上写了
   `@Validated @ModelAttribute` 之后，校验失败时 Spring 默认的反应是
   抛 `MethodArgumentNotValidException`，而不是把错误信息放进模型。
   要让模板里的 `th:errors` 显示出提示，必须在被校验的参数**紧后面**
   加一个 `BindingResult` 参数去接住错误 —— 位置还不能放错，
   它必须紧跟校验对象，中间隔一个参数都不行。

3. **HTML 的表单发不出 PUT 和 DELETE**。`<form method="put">` 浏览器不认，
   会当成 GET 发出去，而且是**静默降级**，不报任何错。所以后台的修改和删除
   全部用 POST，靠地址区分动作：`POST /admin/articles/{id}` 是改，
   `POST /admin/articles/{id}/delete` 是删。删除也不能做成 `<a href>` 链接 ——
   那样浏览器预加载一次就把数据删掉了。

4. **服务端渲染读不到 localStorage**。静态页面那套把"当前身份"存在
   localStorage 里，而服务端渲染时模板是在服务器上执行的，
   localStorage 是浏览器里才有的东西，读不到。改用 `HttpSession` 存，
   服务器自己记着，模板里用 `session.currentUser` 就能取到。

**另外两件事不算"坑"，是这次实实在在踩出来的**：

一是**验证脚本把数据库改了**。写了个自动验证脚本跑那 20 项检查，
其中有一步是"删掉临时建的分类，确认删除功能正常"，脚本恢复数据时
用正则在页面上找刚建的那个分类 ID，模式写的是
`/admin/categories/(\d+)/delete` —— 这个模式在表格里第一个匹配到的
其实是**表格第一行"学习笔记"**，于是脚本把 1 号分类改了名、还改了描述。
跑完查数据库才发现。

恢复的路子是翻 `docs/test_data.sql` —— 那是建库时写的初始数据脚本，
里面记着 `('学习笔记', '课程学习过程中的知识整理')` 这个原始值，
照它改了回去。这脚本一直在那儿，真到要恢复的时候才意识到
**它真正的用处是"记住最初长什么样"**。之后给脚本加了保险绳：匹配到
已知的既有 ID 就跳过；搜索范围也收到 `<table` 之后 —— 页面顶部的提示条里
同样会出现刚建的那个分类名，这是误匹配的另一半原因。

二是 **`mvn spring-boot:run` 不会把 `src/main/resources` 的改动同步过去**。
改完模板刷新页面没变化，一度怀疑是自己 Thymeleaf 语法写错了。
实际原因是 Maven 启动时把资源文件复制进了 `target/classes`，
之后改 `src` 里的文件它就不管了 —— **这件事平时是 IDEA 在帮忙做**，
它会自动同步到 `target`，用命令行跑就没人管。手动把改动的文件复制过去，
热重载立刻生效。

## 四、回顾：这次开发中值得记下的几个点

1. **兜底的异常处理器不能真的"兜住一切"**。测的时候访问了一个不存在的
   文件地址，返回的是"服务器内部错误"外加一整屏异常堆栈 —— 因为
   `GlobalExceptionHandler` 里那个接 `Exception.class` 的方法把
   `NoResourceFoundException`（找不到静态资源）也接走了。
   浏览器请求 `favicon.ico` 就会踩到，日志很快会被刷得没法看。
   已改成单独处理、返回 404 状态码、只记一行 warn 日志。
   **教训是：兜底分支里应该能看出"哪些异常是原本没预料到的"**，
   如果所有异常都能被安静地处理掉，真正的 bug 也会被藏起来。

2. **校验注解不写 `groups` 就等于没写**。`@Validated(XxxGroup.class)`
   只检查属于这个分组的规则，而没写 `groups` 的注解属于 Default 分组，
   **在任何分组下都不会被检查**。这是一个不会报错、也不会有任何提示的坑，
   只能靠写注解时留意。

3. **长度上限要去数据库里查，不能凭感觉写**。`@Size(max = 20)` 写在标题上
   看起来挺合理，但数据库里那一列是 `VARCHAR(200)` —— 白白拒掉了
   180 个字符本来能存的正文。

4. **分页的偏移量和页码是两回事**。`LIMIT 10, 10` 是"跳过前 10 条取 10 条"，
   不是"取第 10 页"。这个换算错一次，翻页的结果就会整体错位，
   而且第一页看起来完全正常，要到翻页时才发现。

5. **整数除法求页数要向上取整**。`total / size` 会丢掉最后一页不满的那些数据，
   正确写法是 `(total + size - 1) / size`。

6. **前端的权限判断挡不住任何人**。它只是让界面好看一点，
   真正的权限校验必须在后端。这一点在写前端时容易忘 ——
   看到按钮藏起来了，就以为别人做不了这件事了。

7. **"查过了"和"查对了"是两回事，否定的结论尤其难验证**。翻查实验一那份
   说明书的目录树时，我判断 `templates/` 是不存在的，还把它删掉了 ——
   依据是一次 `find` 的输出里没有它。可那次命令只列了文件、没列目录，
   一个空目录当然不会出现。**找到了东西能直接看，没找到却得先怀疑
   自己找的方法对不对**，这两件事的可信度差得很远。
   写"某某不存在"之前，换一种方式再确认一遍。

8. **写文档时容易照着"应该是这样"写，而不是照着代码写**。说明书 2.2 节
   原来说搜索是"按标题或正文关键字模糊匹配"，可实际的 SQL 只有
   `WHERE title LIKE ...`，正文压根没参与匹配。写那句话时想的是
   "搜索一般都搜全文"，没有回头看代码。**这类描述写完要对着代码核一遍**，
   因为读的人会把它当成事实。

9. **对着要求逐条核对，不要等做完再回头对**。前五次提交全部完成、
   自以为可以收尾了，这时才把实验三的六条要求拿出来一条条对，
   结果第 6 条（「基于 Thymeleaf 框架完成前端页面设计」）压根没做。
   这一条不是补个字段、加个接口就能了事的，等于整个后台要另做一套。
   前面每一次提交单独看都没问题，问题出在**从没把要求展开成一张清单**。
   如果一开始就逐条列出来、做完一条划掉一条，这件事在第一次提交前就会暴露。

10. **命令行跑和 IDEA 跑不是一回事**。改完模板刷新页面没有变化，
    排查了半天 Thymeleaf 语法，真正的原因是 `mvn spring-boot:run`
    只在启动那一刻把资源文件复制进 `target/classes`，之后改 `src` 里的文件
    它不管 —— 而 IDEA 会自动同步。**同一份代码，换个方式启动，
    行为就不一样**，遇到"改了没生效"时先确认一下自己是怎么跑起来的。

11. **让脚本按"第几个匹配"去定位数据，迟早会定位错**。验证脚本要找出
    刚建的那个分类，用正则从页面 HTML 里匹配 `/admin/categories/(\d+)/delete`，
    结果第一个匹配到的不是刚建的，而是表格第一行"学习笔记"，
    脚本就把 1 号分类改了名。**页面上的文字不是给程序读的数据结构** ——
    同样的分类名在页面顶部的提示条里也会出现一次。真要脚本去认数据，
    应该让它用接口返回的 ID，而不是到渲染好的页面里回头去猜。
    这次能恢复，靠的是建库时那份 `test_data.sql` 里记着的原始值。
