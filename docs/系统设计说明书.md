# 个人知识博客系统 — 系统设计说明书

## 一、系统简介

个人知识博客系统是一个面向个人用户的轻量级博客平台，用于记录和整理学习笔记、技术文章，并对内容进行分类、标注和评论互动。

系统的核心使用场景是：用户注册登录后，把自己的知识整理成文章发表，用分类做一级归档、用标签做多维度标注，读者可以浏览、搜索文章并发表评论。

## 二、功能模块介绍

系统划分为 6 个功能模块，结构见 `功能模块图.png`。

### 2.1 模块总览

| 模块 | 主要职责 | 涉及的数据表 |
|---|---|---|
| 用户模块 | 账号注册、登录退出、个人资料维护 | `user` |
| 文章模块 | 文章的新增、编辑、删除、查看详情 | `article` |
| 分类标签模块 | 维护文章分类和标签 | `category`、`tag`、`article_tag` |
| 评论模块 | 读者对文章发表评论、回复他人的评论、删除评论 | `comment` |
| 搜索筛选模块 | 按关键字检索文章，按作者/分类/标签筛选文章，分页浏览 | `article`、`article_tag` |
| 后台管理模块 | 管理员管理用户和内容 | 全部表 |

### 2.2 各模块详细说明

#### （1）用户模块

负责账号的全生命周期管理，是整个系统的入口。

| 功能 | 说明 |
|---|---|
| 注册账号 | 游客填写用户名、密码、邮箱完成注册，用户名唯一不能重复 |
| 登录退出 | 校验用户名密码，成功后建立会话；退出时销毁会话 |
| 个人资料管理 | 修改邮箱等资料，修改登录密码 |

设计要点：`user` 表用 `role` 字段区分**普通用户**和**管理员**，而不是建两张表。这样后续要扩展角色（比如"编辑"）只需增加枚举值，不用改动表结构。

#### （2）文章模块

系统的核心模块，所有内容都围绕文章产生。

| 功能 | 说明 |
|---|---|
| 发表文章 | 填写标题、正文，选择所属分类 |
| 编辑文章 | 修改自己已发表的文章，修改后自动更新修改时间 |
| 删除文章 | 删除自己的文章，需同时清理其评论和标签关联 |
| 文章详情 | 展示正文内容，并累加浏览量 |

设计要点：`article` 表同时关联**作者**（`user_id`）和**分类**（`category_id`）两个外键；`update_time` 字段设置了 `ON UPDATE CURRENT_TIMESTAMP`，修改记录时数据库自动更新时间，不需要写额外的代码。

#### （3）分类标签模块

提供两种不同维度的内容组织方式，是本系统数据结构设计的重点。

| 功能 | 说明 |
|---|---|
| 分类管理 | 维护文章分类，一篇文章只归属一个分类 |
| 标签管理 | 维护标签，一篇文章可以有多个标签 |

**分类和标签的区别**：

- **分类**是**一对多**关系——一篇文章只能属于一个分类，一个分类下有多篇文章。类似文件夹，是强归属。
- **标签**是**多对多**关系——一篇文章可以有多个标签，一个标签可以贴在多篇文章上。类似便利贴，是弱标注。

因为多对多关系无法直接用外键表达，所以额外拆分出一张关联表 `article_tag`。

#### （4）评论模块

提供读者与作者之间的互动能力。

| 功能 | 说明 |
|---|---|
| 发表评论 | 登录用户对文章发表评论 |
| 回复评论 | 回复某条已有的评论，形成"评论 + 回复"的两层对话 |
| 删除评论 | 删除自己的评论；管理员可删除任意评论；删顶层评论时连带删掉它下面的回复 |

设计要点：`comment` 表关联三个外键——`user_id`（谁评论的）、`article_id`（评论了哪篇）、`parent_id`（挂在哪条顶层评论下面，指向本表），再加一个 `reply_to_user_id` 记录"在回复谁"，保证每条评论都能追溯到明确的来源和对话对象。

**为什么评论只做两层**：回复的回复会被归到同一个顶层评论下（写入时归一化），`parent_id` 永远指向顶层评论。这样查询一棵评论树只需一次 SQL 再按 `parent_id` 分组，删除时一句 `WHERE parent_id = ?` 就能清干净，都不需要递归。代价只是写入时多一次判断，换来读取和删除的简单。

#### （5）搜索筛选模块

| 功能 | 说明 |
|---|---|
| 关键字搜索 | 按**标题**关键字模糊匹配文章 |
| 条件筛选 | 按作者、分类、标签三种维度筛选文章 |
| 分页浏览 | 文章列表按每页固定条数返回，同时给出总页数和上下页标记 |

**搜索、筛选、分页是三件不同的事**，系统里对应三组接口：

- **搜索**是"我输入一段文字去找"——对应 `/article/search`
- **筛选**是"我点一个分类或标签，看它下面有什么"——对应 `/article/author/{userId}`、`/article/category/{categoryId}`、`/article/tag/{tagId}`
- **分页**是"东西太多，一次只看一屏"——对应 `/article/page`

它们彼此独立：搜索和筛选都一次返回全部匹配结果，不分页；分页接口也不接受关键字。

**为什么搜索只匹配标题，不匹配正文**：正文存在 `LONGTEXT` 字段里，对它做 `LIKE '%关键字%'` 用不上索引（通配符开头就断了索引），每搜一次就是一次全表扫描。标题字段短、命中率高，作为搜索入口更合适。正文搜索属于"全文检索"的范畴，需要 MySQL 的全文索引或专门的搜索引擎，超出本系统的范围。

**为什么按标签筛选要连表**：其他几个筛选条件查的都是 `article` 表自己的字段，而"文章有哪些标签"这个信息存在 `article_tag` 关联表里，所以按标签筛选需要 `INNER JOIN` 一次。它和"查这篇文章有哪些标签"（`/article/{id}/tags`）正好是反过来的两条路。

#### （6）后台管理模块

面向管理员的模块，权限高于普通用户。

| 功能 | 说明 |
|---|---|
| 用户管理 | 查看用户列表，禁用或删除违规账号 |
| 内容管理 | 删除任意文章和评论，管理分类和标签 |

**权限边界**：普通用户只能操作**自己**的文章和评论；管理员可以操作**任意**文章和评论。这是本系统权限设计的核心规则。

标签被视作**文章内容的一部分**，所以"给文章贴/取消标签"也归入这条规则：只有文章作者本人和管理员能改，别人不能往你的文章上乱贴标签。判断逻辑在 Service 层统一写成私有方法 `checkPermission`（删文章、删评论、改标签三处共用）。

## 三、数据结构设计

### 3.1 数据表总览

系统共设计 **6 张表**：

| 序号 | 表名 | 中文名 | 作用 |
|---|---|---|---|
| 1 | `user` | 用户表 | 存储注册用户和管理员 |
| 2 | `category` | 分类表 | 存储文章分类 |
| 3 | `tag` | 标签表 | 存储文章标签 |
| 4 | `article` | 文章表 | 存储文章，系统的核心表 |
| 5 | `article_tag` | 文章标签关联表 | 承载文章与标签的多对多关系 |
| 6 | `comment` | 评论表 | 存储评论 |

统一使用 `InnoDB` 引擎（支持事务和外键）和 `utf8mb4` 字符集（支持中文和 emoji）。

### 3.2 各表详细结构

#### 表 1：user（用户表）

存储注册用户和管理员，用 `role` 字段区分身份。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| user_id | INT | 主键，自增 | 用户ID |
| username | VARCHAR(50) | 非空，唯一 | 用户名 |
| password | VARCHAR(100) | 非空 | 密码 |
| email | VARCHAR(100) | | 邮箱 |
| role | TINYINT | 默认 0 | 角色：0-普通用户，1-管理员 |
| create_time | DATETIME | 默认当前时间 | 注册时间 |

#### 表 2：category（分类表）

存储文章分类，与文章是**一对多**关系。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| category_id | INT | 主键，自增 | 分类ID |
| name | VARCHAR(50) | 非空，唯一 | 分类名称 |
| description | VARCHAR(255) | | 分类描述 |

#### 表 3：tag（标签表）

存储文章标签，与文章是**多对多**关系。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| tag_id | INT | 主键，自增 | 标签ID |
| name | VARCHAR(50) | 非空，唯一 | 标签名称 |

#### 表 4：article（文章表）

系统的核心表，外键关联作者和分类。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| article_id | INT | 主键，自增 | 文章ID |
| title | VARCHAR(200) | 非空 | 文章标题 |
| content | LONGTEXT | | 文章正文 |
| user_id | INT | 非空，外键→user | 作者ID |
| category_id | INT | 外键→category | 分类ID |
| view_count | INT | 默认 0 | 浏览量 |
| create_time | DATETIME | 默认当前时间 | 发布时间 |
| update_time | DATETIME | 修改时自动更新 | 最后修改时间 |

**设计说明**：

- `content` 用 `LONGTEXT` 而不是 `VARCHAR`，因为文章正文长度不可预估，`VARCHAR` 最大只有 65535 字节。
- `update_time` 设置了 `ON UPDATE CURRENT_TIMESTAMP`，修改记录时由数据库自动维护，避免忘记手动赋值。
- `view_count` 默认 0，展示文章详情时执行 `+1` 更新。

#### 表 5：article_tag（文章标签关联表）

承载文章与标签的**多对多**关系，是本系统 6 张表（而非 5 张）的原因。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| article_id | INT | 联合主键，外键→article | 文章ID |
| tag_id | INT | 联合主键，外键→tag | 标签ID |

**设计说明**：

- 采用 `(article_id, tag_id)` **联合主键**，从数据库层面保证同一篇文章不会重复贴同一个标签。
- 这张表不含业务字段，只存两个外键，专门用来表达"哪篇文章有哪个标签"。
- 多对多关系必须拆表的原因：`article` 表的一行放不下"多个标签"，`tag` 表的一行也放不下"多篇文章"，只能另起一张表记录两两对应关系。

#### 表 6：comment（评论表）

存储评论和回复。这是一张**自联系**表：`parent_id` 指向本表的另一行。

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| comment_id | INT | 主键，自增 | 评论ID |
| content | VARCHAR(500) | 非空 | 评论内容 |
| user_id | INT | 非空，外键→user | 评论人ID |
| article_id | INT | 非空，外键→article | 所属文章ID |
| parent_id | INT | 外键→comment | 所属顶层评论ID，NULL 表示这条本身就是顶层评论 |
| reply_to_user_id | INT | 外键→user | 被回复人的用户ID，NULL 表示直接对文章评论 |
| create_time | DATETIME | 默认当前时间 | 评论时间 |

- `parent_id` 决定这条评论**挂在哪里**（树的形状），`reply_to_user_id` 决定它**在对谁说话**（页面显示成"回复 @某某"）。只留 `parent_id` 的话，两个人互相回复后页面就分不清谁在跟谁说话了。
- `reply_to_user_id` 由后端根据 `parent_id` 指向的那条评论的作者推导，**不接受前端传入**，防止伪造成"某某回复了你"。

### 3.3 表间关系汇总

| 关系 | 类型 | 说明 |
|---|---|---|
| 用户 — 文章 | 1 : N | 一个用户可发表多篇文章，一篇文章只有一个作者 |
| 分类 — 文章 | 1 : N | 一个分类包含多篇文章，一篇文章只属于一个分类 |
| 用户 — 评论 | 1 : N | 一个用户可发表多条评论 |
| 用户 — 被回复 | 1 : N | 一个用户可被回复多次（`reply_to_user_id`） |
| 文章 — 评论 | 1 : N | 一篇文章可拥有多条评论 |
| 评论 — 评论 | 1 : N | **自联系**：一条顶层评论下面可挂多条回复（`parent_id`） |
| 文章 — 标签 | **M : N** | 一篇文章可有多个标签，一个标签可贴在多篇文章上（由 `article_tag` 承载） |

### 3.4 外键约束清单

系统共建立 8 个外键约束，用于保证数据的参照完整性，避免出现"文章的作者不存在"这类脏数据。

| 约束名 | 所在表 | 字段 | 引用 |
|---|---|---|---|
| fk_article_user | article | user_id | user(user_id) |
| fk_article_category | article | category_id | category(category_id) |
| fk_at_article | article_tag | article_id | article(article_id) |
| fk_at_tag | article_tag | tag_id | tag(tag_id) |
| fk_comment_user | comment | user_id | user(user_id) |
| fk_comment_article | comment | article_id | article(article_id) |
| fk_comment_parent | comment | parent_id | comment(comment_id) |
| fk_comment_reply_user | comment | reply_to_user_id | user(user_id) |

| 页面 | 面向谁 | 说明 |
|---|---|---|
| `index.html` | 访客 | 首页，文章卡片列表 + 搜索 + 翻页 |
| `post.html` | 访客 | 文章详情，正文 + 标签 + 两层评论区 |
| `browse.html` | 访客 | 分类与标签浏览，左栏选条件、右栏出文章 |
| `manage.html` | 内容维护者 | 管理后台，四个模块的增删改查 |
| `test.html` | 开发阶段的自己 | 接口测试台，每个接口一个按钮，能看到请求和响应 |

前三者是**博客前台**，是真正给人读的界面；`manage.html` 是**管理后台**；
`test.html` 是实验二留下的自测工具页，配色和排版都是"工具风"，
和前台有意做得不一样。

页面上**不嵌任何数据**，所有内容都是打开后用 `fetch` 调后端接口取回来的，
所以改数据不用重新部署页面。

**为什么不引前端框架**：这个项目的重点是后端的分层和数据设计。
引一个前端框架就得多一套 Node.js 环境和构建流程，别人拿到代码还得先
`npm install` 才能跑起来 —— 对一个 Java 项目来说是额外的负担。
原生 JavaScript 的代价是有些事要自己做（拼 HTML 字符串、算页码条、防 XSS），
换来的是"启动 Spring Boot 就能打开看"，零配置。

### 4.2 各层职责

| 层次 | 包名 | 职责 | 不该做什么 |
|---|---|---|---|
| 控制层 | `controller` | 接收 HTTP 请求，解析参数，触发参数校验，返回结果 | 不写业务逻辑，不直接操作数据库 |
| 业务层 | `service` | 业务规则、权限判断、检查外键指向的记录是否存在 | 不直接写 SQL；不判断字段格式（那是校验注解的活，见 4.5） |
| 数据访问层 | `mapper` | 执行 SQL，与数据库交互 | 不写业务逻辑 |
| 实体层 | `entity` | 承载数据，与数据库表一一对应；顺带声明字段的校验规则 | 不写业务方法 |

**为什么要分层？** 每层只做一件事，职责清晰。修改数据库操作只动 `mapper`，修改业务规则只动 `service`，各层互不干扰。

**`exception` 包是干什么的？** 它不算一个独立的层，而是给业务层和控制层搭的桥。业务层发现"这个操作不允许"（比如用户名重复），就抛一个 `BusinessException`；`GlobalExceptionHandler` 接住它，转成 `{"code":500,"msg":"用户名已存在"}` 返回浏览器。有了这条通道，各层都不用写 try-catch，也不用各自拼错误信息。

### 4.3 一次请求的处理流程

以"查询文章列表"为例：

```
浏览器访问 /article/list
        ↓
ArticleController.list()          控制层：接收请求
        ↓
ArticleService.listAll()          业务层：处理业务逻辑
        ↓
ArticleMapper.selectAll()         数据访问层：调用 SQL
        ↓
ArticleMapper.xml 里的 SELECT     真正执行的 SQL 语句
        ↓
MySQL 的 knowledge_blog 数据库    查出数据
        ↓
原路返回，包装成 JSON              { "code": 200, "msg": "操作成功", "data": [...] }
```

### 4.4 关键配置说明

**application.properties**（提交到仓库）：

| 配置项 | 作用 |
|---|---|
| `spring.datasource.url` | 数据库连接地址，指定连 `knowledge_blog` |
| `mybatis.mapper-locations` | 指定 XML 映射文件的位置 |
| `mybatis.type-aliases-package` | 实体类包名，XML 里可简写类名 |
| `mybatis.configuration.map-underscore-to-camel-case` | 下划线字段名自动转驼峰（`user_id` → `userId`） |

**数据库密码的处理**：密码不写进主配置文件，而是放在 `application-local.properties` 里，该文件已被 `.gitignore` 排除，不会提交到代码仓库，避免密码泄露。

### 4.5 参数校验的位置

字段的合法性（非空、长度、格式）用**注解**写在实体类上，
由 Controller 参数上的 `@Validated` 触发检查 —— 也就是说，
这一步发生在**进入业务层之前**：

```
请求到达 Controller
      ↓
@Validated 检查实体类上的注解 ── 不通过 → 直接返回错误，Service 根本不会被调用
      ↓ 通过
Service 处理业务规则（重名、权限、外键指向的记录是否存在……）
      ↓
Mapper 执行 SQL
```

这样分工的结果是：**业务层里没有一行代码在判断"这个字段是不是空的"**，
它只管业务规则。校验注解回答的是"字段本身合不合法"，
Service 回答的是"在当前数据下这个操作允不允许"，两者不重叠。

**校验分组解决"同一个类要应付两种场景"的问题**：新增文章时 `articleId`
还不存在（由数据库生成），修改时却必须填；注册时用户名密码必填，
改资料时不传表示保留原值。一套规则没法同时满足两边，
所以定义 `ValidGroup.Create` 和 `ValidGroup.Update` 两个空接口当作"标签"，
注解和 `@Validated` 各带一个。

> ⚠️ 写注解时**必须显式写 `groups`**。不写 `groups` 的注解属于 Default 分组，
> 而 `@Validated(某个分组)` 只检查属于该分组的规则 —— 落在 Default 分组下的注解
> 在任何分组里都不会被检查，等于白写。这个坑不报错、也没有任何提示。

**校验失败和业务失败从同一个出口返回**：两者最终都由 `GlobalExceptionHandler`
转成 `{"code":500,"msg":"..."}`。区别是校验失败的提示取自注解里的 `message`，
而且会**把多条拼起来一起返回**（比如"文章正文不能为空；文章标题不能为空"）——
否则用户改一条提交一次，来回好几轮才能提交成功。

**长度上限要和数据库对齐**：`@Size(max = 200)` 这样的数字不是凭感觉定的，
是照着 `schema.sql` 里字段的真实长度写的，这样校验拦下的正好就是数据库会拒绝的，
不会出现"校验放行了、写库时却报字段太长"。唯一的例外是 `article.content`，
它在数据库里是 `LONGTEXT`（能存 4GB），在 Java 这边给它编一个长度上限反而是错的，
会拒掉数据库本来存得下的正文 —— 所以那个字段只写了 `@NotBlank`，没有 `@Size`。

### 4.6 两套页面做法：静态页面 vs 服务端渲染

系统里有两套管理后台，功能完全一样，做法完全不同。
这不是重复建设 —— 实验三第 6 条要求基于 Thymeleaf 完成一套页面，
而原有的静态版已经写好了，删掉可惜，留着正好当对照。

| | 静态版 `manage.html` | Thymeleaf 版 `/admin/*` |
|---|---|---|
| 页面放在 | `resources/static/` | `resources/templates/` |
| 怎么访问 | 地址就是文件路径，`/manage.html` | 由控制器决定，`/admin/articles` |
| 浏览器拿到什么 | 一个空壳，表格的 `<tbody>` 里是空的 | 内容已经填好的完整 HTML |
| 数据怎么来 | 浏览器再发十几个请求拿 JSON，用 JS 拼出来 | 服务器渲染时拼进去，不用再发请求 |
| 控制器注解 | `@RestController`（返回值当 JSON） | `@Controller`（返回值当模板名） |
| 表单怎么改数据 | JS 发 `fetch` 的 PUT / DELETE | 普通 `<form>` 提交，全是 POST |
| 身份记在哪 | 浏览器的 localStorage | 服务端的 Session |

**两种做法没有绝对优劣**，看场景：

- 静态页面把渲染压力放在浏览器，服务器只管发文件和 JSON。
  适合交互频繁、需要局部刷新的界面 —— 翻页时只换表格，导航栏不用重画。
- 服务端渲染的页面，浏览器拿到就能看，不依赖 JS；搜索引擎爬虫也能直接读到内容。
  代价是每次交互都要重新渲染一整页。

**改造过程中撞到的四个坑**（都是这类项目的通病）：

1. **全局异常处理器会把页面异常也转成 JSON**。
   `GlobalExceptionHandler` 原本是 `@RestControllerAdvice`（管所有包），
   它返回的全是 JSON。新加的页面控制器一旦出错，本该显示错误页面，
   结果被它接管转成一屏 JSON，页面直接白屏，排查时完全摸不着头脑。
   改法是加 `basePackages = "cuit.mygit.controller"`，把管辖范围**收窄回原来那个包**，
   放在 `web` 包里的页面控制器就不受它管了。

2. **表单校验要用 `@Validated` + `@ModelAttribute`，且 `BindingResult` 必须紧跟其后**。
   这套写法和 JSON 接口那边的 `@Validated` + `@RequestBody` 不一样：
   少了 `BindingResult` 这个参数，校验失败时 Spring 会直接抛异常，
   方法体根本执行不到，`th:errors` 里永远是空的。

3. **HTML 表单发不出 PUT 和 DELETE**。
   浏览器的 `<form>` 只认 GET 和 POST，写 `method="put"` 会被静默降级成 GET。
   JSON 接口那边能用 PUT/DELETE 是因为那些请求是 JS 发的，不受这个限制。
   所以后台的增删改全用 POST，靠**路径**区分动作：
   `POST /admin/articles/3/delete` 是删除，`POST /admin/articles/3` 是保存修改。

4. **服务端渲染读不到 localStorage**。
   静态版把"当前登录的是谁"存在浏览器里，只有 JS 读得到；
   服务器渲染页面时看不见它。所以改成存 `HttpSession` ——
   选一次身份存在会话里，后续每次请求服务器自己就知道你是谁。

**这次一共动了哪些文件**：`pom.xml` 加 Thymeleaf 依赖；
新增 `cuit.mygit.web.AdminController`；新增 `templates/admin/` 下 6 个模板；
新增 `static/css/admin.css`；`GlobalExceptionHandler` 加了一行 `basePackages`。
**Service 层的 5 个接口和 5 个实现类一行都没改** —— 这正是分层的价值：
换掉整套前端，业务逻辑原封不动。

**评论模块**

| 方式 | 路径 | 说明 |
|---|---|---|
| GET | `/comment/article/{articleId}` | 某篇文章的评论（平铺返回，按 `parentId` 分组成两层） |
| GET | `/comment/user/{userId}` | 某个用户的评论 |
| POST | `/comment/add` | 发表评论；请求体带 `parentId` 时就是回复 |
| DELETE | `/comment/{id}?operatorId=` | 删除评论（删顶层评论会连带删它的回复） |

> 评论模块**没有修改接口**。评论发出去就固定了，写错了只能删掉重发 ——
> 整个系统里只有它是完整的增删查、没有改，这是有意设计的。

**两点说明**

1. **`operatorId` 是什么**：删文章、删评论、改标签这三个操作需要判断"现在是谁在操作"。
   系统还没做登录会话，所以由调用方在 URL 上把当前用户 ID 带过来。
   等以后接了登录功能，这个参数从会话里取，接口本身不用改。

2. **为什么 `/article/search` 要写在 `/article/{id}` 前面**：`{id}` 是路径变量，
   能匹配 `/article/` 底下的**任意一段** —— 包括匹配上 `search` 这个词。
   如果 `{id}` 排在前面，访问 `/article/search` 时 Spring 会先把 `search`
   当成文章 ID 去转整数，然后失败。照理说 Spring Boot 3 之后用的路径匹配器
   会优先选"更具体"的那个，但依赖这条规则容易踩坑，写在前面最省心。

## 六、设计要点小结

1. **多对多关系拆表**：文章与标签的 M:N 关系拆出 `article_tag` 中间表，用联合主键防止重复关联。
2. **外键保证完整性**：6 个外键约束防止出现指向不存在记录的脏数据。
3. **权限用单字段表达**：`user.role` 一个字段区分普通用户和管理员，比建两张表简单，且便于扩展。
4. **时间字段自动维护**：建表时设置默认值和自动更新，不依赖应用代码赋值。
5. **统一字符集和引擎**：全部 `utf8mb4` + `InnoDB`，支持中文、emoji，支持事务和外键。
6. **分层架构**：控制层、业务层、数据访问层、实体层各司其职，便于维护和扩展。
7. **敏感信息隔离**：数据库密码通过独立的本地配置文件管理，不进入版本控制。
8. **参数校验前置**：字段的合法性用注解声明、在进业务层之前检查，所以业务层里没有一行判断"这个字段是不是空的"的代码。
9. **分页信息一次给全**：`PageResult` 把总条数、总页数、上下页标记一起返回，前端不用再发一次请求问总数。
10. **界面零构建**：前端是纯静态页面，由 Spring Boot 直接发布，不引入 Node.js 工具链 —— 拿到代码启动就能看。
11. **前端不承担权限**：界面上按钮的显隐只是"少让用户白点一次"，真正的权限校验在后端 Service 层。前端的身份存在浏览器本地，谁都能改，所以它挡不住任何人。
